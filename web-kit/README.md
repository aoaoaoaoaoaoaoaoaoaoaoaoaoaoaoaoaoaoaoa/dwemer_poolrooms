# Poolrooms Web Kit

This directory is the canonical lightweight browser projection of Brass
Poolrooms. It is not the full WebGPU renderer: static foundry witnesses provide
the exact first render and fallback, while `riptide.js` adds finite analytic
WebGL2 wakes beneath ordinary document content.

`src/` contains authored browser code. `dist/` contains release witnesses and
is regenerated by `scripts/web-kit forge`. `scripts/web-kit check` rebuilds
every mechanically reproducible artifact, checks the deliberate source locks,
and assembles the deterministic release archive beneath Cargo's target directory.
The ordinary hosted gate uses `scripts/web-kit verify`: it checks the same
source locks and exact output seals without requiring the pinned media forge.
Every package and release still performs the complete rebuild.

The payload contains:

- `brass-tiles.png` and its 2×/3× siblings: the named deep-rest floor preset,
  rendered directly from the current Poolrooms WGSL;
- `chrome/frame-*.png`: exact flat plate perimeters for CSS `border-image`;
- `chrome/monoglyph-atlas.png`: rest, held, and four recoil poses rendered by
  the public `Monoglyph` mechanism;
- `chrome/platform-die-atlas.png`: seven foundry-rendered platform marks;
- `riptide.js`: a bounded WebGL2 projection of Poolrooms water beneath an
  ordinary DOM, including opt-in passing rain; and
- `poolrooms.css`: optional generic layout and pose selection.

The source locks are synchronization boundaries, not claims that every web
projection is generated from one universal intermediate language. A change to
locked Rust or WGSL requires an explicit review of the affected projection.
The floor witnesses themselves are rendered directly from the current WGSL.

When a governing input changes, review the semantic delta, ratify its digest in
`projection.sources`, run `scripts/web-kit forge`, inspect the witnesses, and
ratify the resulting `projection.outputs`. Neither forge nor check rewrites
these ledgers. This small manual approval seam is intentional; all copying,
minification, GPU rendering, raster optimization, manifest assembly, and
consumer synchronization remain mechanical.

Exact forging and publication run on x86_64 Linux with Mesa software GL and the
pinned media tools checked by `scripts/web-kit`. The emitted browser assets are
platform-independent. `verify` remains portable because it reads only the
committed locks and witnesses.

Consumers must pin an exact Poolrooms version. Static sites should copy the
selected files into their own deployment and serve them from the same origin;
the package is a build dependency, not a runtime CDN.

For the generic projection, copy `dist/` intact, load `poolrooms.css`, put
`poolrooms-field` on `body`, and use `poolrooms-frame` with one of the three
frame-material classes. Load `riptide.js` at the end of `body` only when the
optional water response is wanted. The script resolves the density tiles
relative to its own URL, so the kit can inhabit any same-origin directory.
Prefer a versioned deployment directory such as `/poolrooms/0.13.1/`. A site
that keeps stable asset paths must replace the document, SRI seal, asset, and
edge cache atomically.

`data-riptide-rain="passing"` on `body` admits rain ten seconds into the page
lifetime. Riptide samples a random-phase, low-frequency field four times per
second. Only its upper decile rains; intensity becomes the arrival probability
of finite wakes inside one broad drifting lobe. Dry weather performs no
rendering, and the ordinary reduced-motion and data-saver gates disable the
clock with the rest of Riptide.

`scripts/web-kit package` emits `brass-poolrooms-web-<version>.tar.gz` with a
manifest recording the crate version, source commit and dirty state, web ABI,
byte counts, SHA-256 hashes, and SRI seals. Its normalized order, ownership,
timestamps, and gzip header make identical source produce an identical archive.
`scripts/web-kit publish` admits only a clean `main` checkout tagged
`v<version>`, signs the archive with the configured Git OpenPGP identity, and
attaches the archive, detached signature, and checksum to that GitHub Release.
Consumers should commit their installed manifest and verify it during ordinary
offline builds; network access belongs only to an explicit synchronization
action.
